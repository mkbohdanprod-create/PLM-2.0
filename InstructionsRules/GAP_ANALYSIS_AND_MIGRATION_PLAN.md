На основі глибокого аналізу живої бази даних (Supabase) та коду фронтенду (React), виявлено критичні розбіжності між тим, як система працює зараз, і тим, як вона має працювати за новим стандартом. ## 1. Аналіз розбіжностей (GAP Analysis)

### §1.1 Концепція Паузи (The Pause Shift)
**GAP:** У базі та на UI існує єдиний глобальний статус PAUSED. Історія зберігається в колонці previous_status. 
**Target (Уточнено):** За рішенням користувача, ми залишаємо єдиний глобальний статус PAUSED та продовжуємо використовувати колонку previous_status для відновлення. Це забезпечує зацикленість єдиного макро-етапу "Пауза". Колонка resume_date відповідає за таймер (коли відновити роботу). Функція change_order_status обробляє RESUME.

### §1.2 Двошарова модель (Flat vs Hierarchical)
**GAP:** Фронтенд жорстко хардкодить рядки статусів. 
**Target:** База оперує розширеним Enum Мікро-статусів. Для зручності SQL-запитів додається Generated Column macro_stage, яка автоматично обчислюється базою. Фронтенд використовує Словник для відображення їх згрупованими у 8 Макро-Етапів. СКАСОВАНО: двошарова модель була відхилена, залишилася плоска.

### §1.3 Механіка Регресій (Відкатів)
**GAP:** Таблиця status_transitions (id 7-44) підтримує лише рух "вперед" та "скасовано". 
**Target:** Легалізація регресій (напр., повернення до диспетчера після збою на об'єкті).

### §1.4 Розбиття Заміру на 5 станів
**GAP:** Зараз у БД є лише MEASUREMENT_SCHEDULED та MEASUREMENT_COMPLETED. 
**Target:** Повний ланцюг: SCHEDULED → IN_PROGRESS → FINISHED_ON_SITE → COMPLETED.
Два регресійні шляхи: MEASUREMENT_FAILED (зсув SLA) та MEASUREMENT_CANCELED_BY_MEASURER (без зсуву SLA).

### §1.5 Розбиття Монтажу

**Target:** SCHEDULED → IN_PROGRESS → FINISHED_ON_SITE → COMPLETED. + FAILED (регресія) та INSTALLATION_RECLAMATION.

### §1.6 Новий Макро-Етап «Доставки»

**Target:** Новий пул статусів: DELIVERY_SCHEDULING, DELIVERY_IN_TRANSIT, READY_FOR_PICKUP. Новий дашборд.

### §1.7 Розбиття Конструктиву (Personal Kanban)

## 3. Ризики та Міграційні заходи (Dry-Run Protocol)
Найвища небезпека — у Хвилі 2 при конвертації старих пауз.

**Стратегія (Сироти PAUSED):** Перед міграцією на прод робиться pg_dump продакшн бази. Розгортається staging-копія. Запускається міграційний скрипт UPDATE ... WHERE previous_status = .... Обов'язковий крок: пошук сиріт (замовлення, де status = 'PAUSED', але previous_status IS NULL або містить некоректне/старе значення). Вони виводяться в окремий лог. Аналітик (керівник) приймає рішення по кожному id вручну (встановлює цільовий статус перед накатуванням міграції). Тільки після цього міграція накатується на прод.

---

## 4. Тестовий План
Кожна хвиля завершується тестами (без них реліз заборонено):

1. **Happy Path:** Створити замовлення → План Заміру → AppSheet Webhook → Конструктив → MES → Доставка → Монтаж → Закрито.
2. **Pause Matrix:** На кожному етапі натиснути "Пауза". Переконатися, що статус стає PAUSED_{STAGE}, а після "Відновити" переходить на наступний робочий стан.
3. **Regressions (SLA):** Зробити MEASUREMENT_FAILED. Перевірити, що Таймлайн 1 (Клієнт) зсунувся. Зробити MEASUREMENT_CANCELED_BY_MEASURER. Перевірити, що Таймлайн 1 залишився незмінним.
4. **Security Check (Критично для Хвилі 1):** Спробувати з акаунта Менеджера надіслати прямий HTTP PATCH {"status": "COMPLETED"} або {"resume_date": "2026-10-10"} до таблиці orders через REST API Supabase (напр., через Postman або консоль). Перевірити, що база блокує запит помилкою недостатніх привілеїв, доводячи, що Column-level RLS та REVOKE UPDATE працюють.

## 6. Регламент виконання
Основна модель: агент виконує, керівник тільки затверджує. Керівник не пише код, не запускає команди в БД, не робить бекапи руками. Він приймає рішення в точках, де потрібне підтвердження.

**Стандартний цикл для кожної хвилі:**
1. Агент генерує пакет змін. SQL-міграції, RPC, правки фронтенду, тестові скрипти — все в одному коміті на окремій гілці. Разом з коротким WAVE_N_REPORT.md (що зроблено, що змінилось у схемі, які файли зачеплено, які тести підготовлено).
2. Агент накатує на dev-середовище. Локальний Supabase (npx supabase start) або окремий dev-проєкт. Прогнати міграцію, зібрати фронт, запустити e2e-тести з Розділу 4.
3. Агент готує звіт «до/після». Показує керівнику: SQL-дифи ключових таблиць (\d orders, \d status_transitions), актуальна сигнатура change_order_status, список зачеплених фронт-компонентів, скріни або відео проходження e2e-сценаріїв на dev.
4. Керівник затверджує звіт. Одне з трьох рішень: (а) «Апрув» — переходимо до кроку 5; (б) «Правки» — агент виправляє і повертається до кроку 3; (в) «Стоп» — хвиля відкладається, розбираємось.
5. Для хвиль з міграцією даних (2, 3, 5) — обов'язковий staging dry-run. Агент робить pg_dump прода, розгортає локально, накатує міграцію, збирає таблицю edge-кейсів (напр. «замовлень з status='PAUSED' і порожнім previous_status — N штук, ось їх список»), формує окремий короткий звіт WAVE_N_DRYRUN.md. Керівник дивиться звіт і затверджує стратегію для сиріт (переводити в CANCELLED, повертати в конкретний етап, ігнорувати тощо).
6. Агент накатує міграцію на прод. Перед цим — автоматичний pg_dump прода з міткою часу і назвою хвилі, збережений у папку бекапів. Ніякого «руками».
7. Агент верифікує прод. Прогнати ключові e2e-сценарії з Розділу 4 на проді (з тестовими замовленнями). Перевірити відсутність помилок у консолі фронта і в логах Supabase.
8. Агент виконує Розділ 5 (Memory Hygiene). Оновлює CURRENT_STATE.md, чистить BUGS_AND_TECH_DEBT.md, оновлює order_stages_and_pause_rules.md (або цільовий документ) новим переліком enum, інкрементує версію GAP_ANALYSIS_AND_MIGRATION_PLAN.md.
9. Керівник підтверджує закриття хвилі. Дивиться на оновлений CURRENT_STATE.md, каже «закриваємо» або «повертайся до кроку N».

**Дії, які агент НЕ робить без явного затвердження:**
- Не накатує SQL на прод без апруву (крок 4).
- Не приймає архітектурні рішення, які змінюють план (напр. «відмова від масивів allowed_view_regions»). Такі рішення виносяться в план як новий пункт §1.X — потребує рішення керівника.
- Не видаляє пункти з BUGS_AND_TECH_DEBT.md без явного «цей борг закрито хвилею N». Просто «застаріле» — не привід.
- Не редагує GAP_ANALYSIS_AND_MIGRATION_PLAN.md без інкременту версії.
