# Бізнес-процес: Комунікація та Активності (Actionable Tasks over Records)

Цей документ описує логіку роботи з комунікацією диспетчера та клієнта, а також технічний план реалізації через архітектуру Активностей (Activities).

## 1. ОПИС БІЗНЕС-ЛОГІКИ

### 1.1 Архітектура "Actionable Tasks over Records"
**Ключовий принцип:** Замовлення живе своїм життям (FSM - кінцевий автомат), воно рухається по статусах і потрапляє на планування (Ганту). 
Комунікація — це окрема сутність, яка "прилипає" до замовлення і живе паралельно. Вона **не змінює статусу замовлення**.

Замість одного поля "дата продзвону" в замовленні, ми використовуємо **Активності (Activities)**. Це точкові задачі, які можуть мати різні типи:
- `CALL` — Продзвонити клієнта
- `SMS` — Написати SMS
- `EMAIL` — Написати email
- `MEETING` — Домовитись про зустріч
- `INTERNAL_NOTE` — Задача колезі (напр. технолог, перевір креслення)
- `OTHER` — Інше

Замовлення та активності виводяться в єдиному списку (впереміш). Диспетчер сортує цей список за **датою найближчої активності**, і опрацьовує їх незалежно від того, на якому етапі знаходиться замовлення. 

### 1.2 Життєвий цикл автоматичних активностей

Замість того, щоб міняти поле в замовленні, автоматика створює нові активності:

1. **Нове замовлення (MEASUREMENT_SCHEDULING)**
   - При потраплянні в статус `MEASUREMENT_SCHEDULING`, система автоматично створює активність типу `CALL` на `поточний час + 4 години`.

2. **Попередньо заплановані (MEASUREMENT_SCHEDULED)**
   - При призначенні дати виїзду, попередня активність може закриватись, і автоматично створюється нова активність типу `CALL` на **1 добу до** планової дати виїзду.

3. **Замовлення на Паузі (PAUSED)**
   - Якщо вказана дата виходу з паузи, автоматично ставиться пропозиція активності типу `CALL` за **1 день до неї**.
   - **Критична вимога до UI:** У вікні (модалці), де диспетчер пише причину паузи, **обов'язково** має бути можливість відразу змінити цю запропоновану дату продзвону і вписати текстовий коментар до цього продзвону.

4. **Зафіксовані замовлення (Пішли в роботу)**
   - Коли замовлення переходить у роботу (наприклад, Інженерія чи Виробництво), активності типу "Продзвон диспетчера" більше не створюються автоматично. Але будь-хто (менеджер, конструктор) може створити свою активність.

### 1.3 Закриття активності та Історія

- Коли диспетчер (або інша роль) завершує активність, він натискає «Виконано».
- Система обов'язково запитує **Підсумок (Outcome)**: `ANSWERED`, `NO_ANSWER`, `REFUSED`, `RESCHEDULED`, `DONE` та **Текстовий коментар (Outcome Notes)**.
- Якщо результат означає, що питання не закрите (наприклад, `NO_ANSWER` або `RESCHEDULED`), система одразу пропонує створити нову активність на інший час.
- Виконана активність не видаляється, а переходить у статус `COMPLETED` і назавжди залишається в Історії Комунікації замовлення, формуючи повний "журнал" спілкування з клієнтом.

## 2. ТЕХНІЧНА РЕАЛІЗАЦІЯ

### 2.1 База Даних (PostgreSQL / Supabase)

1. **Нові ENUM типи:**
   - `activity_type`: 'CALL', 'SMS', 'EMAIL', 'MEETING', 'INTERNAL_NOTE', 'OTHER'
   - `activity_outcome`: 'ANSWERED', 'NO_ANSWER', 'REFUSED', 'RESCHEDULED', 'DONE'

2. **Створення таблиці `order_activities`:**
   ```sql
   CREATE TABLE public.order_activities (
       id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
       order_id uuid REFERENCES public.orders(id) ON DELETE CASCADE,
       title text NOT NULL,
       activity_type public.activity_type NOT NULL,
       planned_at timestamptz NOT NULL,
       comment text,
       status text DEFAULT 'PENDING' CHECK (status IN ('PENDING', 'COMPLETED', 'CANCELLED')),
       outcome public.activity_outcome,
       outcome_notes text,
       assigned_to_role text, -- Для кого задача (DISPATCHER, CONSTRUCTOR)
       created_by uuid REFERENCES auth.users(id),
       completed_by uuid REFERENCES auth.users(id),
       created_at timestamptz DEFAULT now(),
       completed_at timestamptz
   );
   ```

3. **Обчислювальне поле для сортування (RPC):**
   Щоб мати єдине джерело правди без денормалізації таблиці `orders`, створюється функція `next_activity_at(order_row orders) RETURNS timestamptz`, яка повертає дату найближчої `PENDING` активності. Фронтенд використовує її для сортування загального списку.

4. **Зміни в тригерах / RPC:**
   - В `create_order`, `change_order_status`, `assign_measurement` — замість роботи з полем `planned_call_date`, створюються або закриваються записи в `order_activities`.

### 2.2 Фронтенд (React)

1. **Завантаження даних (`OrdersList.tsx`):**
   - Робиться запит до замовлень і запит до `order_activities`.
   - Замовлення сортуються за RPC-полем `next_activity_at`.

2. **Відображення елементів списку:**
   - Замовлення та Активності виводяться єдиним потоком.
   - Візуальна різниця: Замовлення має іконку "доручення" і бейдж статусу. Активність має іконку типу (📞, ✉️, 📝), тег задачі і прив'язку до номера замовлення.

3. **Картка замовлення (`OrderCard.tsx`):**
   - Розділ "Комунікація та Задачі": відображає стрічку всіх PENDING та COMPLETED активностей.
   - Кнопка "+ Нова активність".
   - Модалка виконання активності з обов'язковим вибором `outcome` та введенням `outcome_notes`.

## 3. POST-MORTEM ТА ЗАСВОЄНІ ПРАВИЛА (LESSONS LEARNED)

### 3.1. Перевантаження (Overloading) функцій у Supabase / PostgreSQL
При додаванні нових параметрів до існуючої RPC-функції (наприклад, `change_order_status`), якщо нові параметри мають значення за замовчуванням (`DEFAULT NULL`), створюється **нова сигнатура** функції. Але стара сигнатура (з меншою кількістю параметрів) залишається в базі даних! 
Через це, коли фронтенд або PostgREST намагається викликати функцію з меншою кількістю параметрів, база даних видає помилку: `Could not choose the best candidate function between...`, оскільки вона не знає, чи викликати стару функцію, чи нову (оскільки у нової аргументи дефолтні).

**ПРАВИЛО:** Завжди, коли ми оновлюємо сигнатуру функції (додаємо параметри, навіть з DEFAULT), ми **ЗОБОВ'ЯЗАНІ** явно прописати `DROP FUNCTION IF EXISTS назва_функції(старі, типи, аргументів);` для всіх попередніх версій цієї функції безпосередньо ПЕРЕД новим `CREATE OR REPLACE FUNCTION`.

### 3.2. Виконання глобальних команд
**ПРАВИЛО:** Заборонено запускати `supabase db reset` або будь-які інші руйнівні/глобальні команди без прямої команди "Приступай" або "виправляй" від користувача, навіть якщо помилка очевидна. Спочатку діагностика, пояснення плану виправлення, і тільки після команди — виконання.
