## 🔁 Якщо ти бачив NestJS-версію: куди що поділось

Ми **нічого не викинули з вимог** — просто переклали важкий стек на вбудовані інструменти Supabase. Ось відповідність, щоб було спокійно:

| У NestJS-версії (відхилено) | Що замість цього на Supabase |
| :--- | :--- |
| Backend: NestJS-моноліт | Логіка в **Edge Functions** + функціях / тригерах у базі |
| ORM + міграції: Prisma | Міграції Supabase (SQL-файли) |
| БД: Postgres + PostGIS | Postgres усередині Supabase (PostGIS — розширенням) |
| Redis + BullMQ (черги, відкладені задачі) | **Черга в базі (pgmq) + розклад (pg_cron)** — нічого окремо не ставимо |
| Redis Streams (шина подій) | **Database Webhooks + Realtime** (+ черга) |
| Outbox + DLQ (щоб подія не загубилась) | Черга живе в тій же базі → та сама гарантія «в одній транзакції»; невдалі йдуть у чергу-відстійник |
| Auth: Lucia/Auth.js + Google SSO | **Supabase Auth** (email + Google) — вбудовано |
| Файли: MinIO / R2 | **Supabase Storage** (S3-сумісне, пресигновані посилання) |
| Геокодер: self-host Nominatim | **Хмарний геокодер** на старт; self-host пізніше, якщо треба |
| Sentry + Prometheus / Grafana / Loki (self-host) | Вбудовані логи Supabase + **Sentry** (безкоштовний) на фронт |
| Формальні OpenAPI / AsyncAPI | Легкі описи подій (як `mes-contract.md`) — без важкої формалізації на старті |
| Multi-tenancy: branch_id + middleware | **branch_id + правила доступу (RLS)** — те саме, вбудованим |
| Audit: підписник на шину | **Аудит через тригери** (append-only) — простіше й спрацьовує для будь-якого писача |
| Карти: MapLibre + OSRM | **Без змін** — однакове в обох планах |
| Frontend: React | **Без змін** — React (SPA на Vite) |

**Висновок:** та сама система, зібрана меншими силами. Жодна вимога не втрачена.

## 📖 Словничок (Supabase по-людськи)

Щоб слова не лякали — ось усе, що треба розуміти:

- **Таблиця** — список рядків, як аркуш в Excel.
- **RLS (правила доступу)** — правила в самій базі: «хто які рядки може бачити й міняти». Це **головний замок** системи.
- **Функція в базі (RPC)** — маленький шматок логіки прямо в базі, який фронт викликає по імені. Через неї міняємо статуси й робимо все, що треба перевіряти.
- **Edge Function** — маленька серверна функція. Потрібна для зв'язку із зовнішнім світом (AppSheet, геокодер, телефонія).
- **Тригер** — «коли рядок змінився, база сама щось робить» (наприклад, пише в журнал).
- **Realtime** — екран оновлюється сам, коли дані змінились (без F5).
- **Storage** — сховище файлів (фото, креслення, акти) з безпечними посиланнями.
- **Auth** — вхід користувачів (email + Google). Уже вбудований у Supabase.
- **Черга + розклад (pgmq, pg_cron)** — «зроби це пізніше» або «зроби за розкладом» (нагадування, нічні задачі). Усе живе всередині бази, нічого окремо не ставимо.

## 🧭 Що вирішено / що ще обрати / що ігноруємо

**✅ Вирішено:**
- База і бекенд — **Supabase**.
- Вхід — **Supabase Auth** (email + Google).
- Карти — **MapLibre** (показ мапи) + **OSRM** (маршрути). 
- **Геокодер** (адреса → координати): **LocationIQ** (готовий хмарний сервіс).
- **Регіони та Філії:** Замість простої філії діє гнучка ієрархія «Регіон → Філія». У доменних таблицях має бути тільки `branch_id`, а регіон береться через довідник `branches -> regions`. Не дублювати `region_id` у кожній таблиці (це створить неузгодженість при переїзді філії). Регіони можна створювати. На старті: Центр, Південь, Захід, Варшава.
- **Додаток для Замірів / Монтажів:** Оскільки вибір платформи ще відкритий (AppSheet чи власний додаток), ми будуємо універсальний **API-приймальник (через Edge Functions)**. Завдяки цьому нашому бекенду буде абсолютно байдуже, що ви оберете — будь-який застосунок просто відправлятиме туди JSON-дані.
- **Залізне правило:** браузер **ніколи не пише напряму** у важливі таблиці. Будь-який запис, що потребує перевірки, іде через функцію в базі / Edge Function. RLS — замок. *(Саме на цьому горів прототип — там перевірки були в браузері, тож будь-хто міг зробити себе адміном.)*

## 💻 Стек технологій та Дизайн
Щоб не було "чорних скриньок", ось точний набір інструментів і мов, на яких ми це будуємо:

1. **База даних (Серце):** **PostgreSQL** (під капотом Supabase). 
   - *Мова:* **SQL** (PL/pgSQL). Усі правила, тригери та безпека (RLS) пишуться суто на SQL всередині бази.
2. **Серверна логіка (Шлюзи / API):** **Edge Functions** (Supabase). 
   - *Мова:* **TypeScript** (виконується на движку Deno). Це строгий JavaScript, який не дає зробити дурних помилок.
3. **Фронтенд (Інтерфейс користувача):** **React** + **Vite**.
   - *Мова:* **TypeScript**. 
   - Чому вони? React — це золотий стандарт для створення складних інтерактивних систем (а не просто статичних сайтів). Vite робить так, щоб проект запускався миттєво.
4. **Дизайн та Стилістика (CSS):** 
   - *Підхід:* Ексклюзивний, преміальний інтерфейс на базі **Vanilla CSS / CSS Modules**. 
   - *Ергономіка робочих зон:* "WOW-ефект" (ефект матового скла, мікро-анімації, градієнти) ми використовуємо для вітринних екранів, логіну та статистики. Але там, де диспетчер працює 8 годин (таблиці, Канбан) — дизайн буде максимально чистим, контрастним і зручним для читання, як у топових світових продуктах.
   - *Складні компоненти (Календарі, Випадайки):* Для механіки таких елементів ми використаємо "голі" невидимі примітиви (**Radix UI**). Вони дають ідеальну надійність (управління з клавіатури, фокус), а візуальну "обгортку" я напишу нашим чистим CSS.
   - Я навмисно **уникаю** шаблонних бібліотек і "смітників з десятків класів" (як Tailwind CSS). Чистий CSS дає нам абсолютний контроль і зберігає код ідеально читабельним.

## 🔧 Ключові виправлення (що робимо інакше, ніж у прототипі)

Зведено в одному місці — щоб не губилось. Деталі кожного пункту — у відповідних етапах нижче.

**Безпека (тут прототип горів найсильніше):**
- Охорона даних — у базі (RLS + функції), **не в браузері**. У прототипі будь-хто залогінений міг зробити себе адміном — більше ні.
- Браузер **не пише напряму** у важливі таблиці; запис із перевіркою — лише через функцію.
- Секрети (ключі, паролі) — **не в коді**. (У старому репозиторії лежав пароль суперюзера в git — так не робимо.)
- Нова людина отримує **мінімальні** права за замовчуванням, ніколи не «Адмін».

**Дані:**
- **Один список людей** (людина = і вхід, і працівник), а не два окремі, як у прототипі.
- Колонка **«філія»** у всіх таблицях з першого дня.
- **Не видаляємо назавжди — ховаємо** + причина. (Прототип робив фізичне видалення.)
- **Журнал змін** через тригери. (Прототип не мав жодного.)
- Замовлення **розбите на кілька таблиць**, а не 150 колонок в одній.
- **Площа і гроші — числа**, не текст. (У прототипі текстом — ламало статистику й зарплату.)
- Унікальний код UUID (внутрішній) + окреме поле `external_id` (Номер з 1С), яке диспетчер копіпастить при створенні. Свій людино-читабельний номер не генеруємо — джерело правди для номера це 1С.
- На вході: перевірка дублів + одна картка з прапорцем `is_incomplete`. Картка одразу видима всім, але з міткою «⚠ Неповна», якщо не всі важливі поля заповнені. Перехід далі по машині станів блокується, поки прапорець не знято.

**Статуси:**
- Статус міняється **лише через одну функцію** з перевіркою дозволених переходів. (Прототип ставив будь-який статус напряму.)
- Зберігаємо **попередній статус** — для коректного виходу з «Паузи».
- Кнопки, які не можна натиснути, **ховаємо або робимо сірими** — не даємо помилку.
- **Пропуск етапів за типом** («по кресленню» / «без монтажу»).

**Одночасна робота (кілька людей — одне замовлення):**
- **Замок** + **перевірка версії** + **живе оновлення**. (У прототипі «блокування» жило лише в браузері, тобто не блокувало нічого.)

**Решта:**
- Карти: **MapLibre + OSRM + окремий геокодер** з ручним піном і кешем. (Прототип бив публічний Nominatim з браузера — проти правил.)
- Файли — у **Storage** з безпечними посиланнями.
- **AI лише читає**, ключ — на сервері. (Прототип: ключ у браузері, AI писав у базу, ще й брехливий напис «дані не йдуть третім особам».)
- Бекапи включають **файли** + тестове відновлення раз на місяць.
- **50 користувачів ≠ велика команда** → важкий стек не потрібен.

## ♻️ Прості правила для кожного кроку (щоб не накопичувати костилі знову)

- Зміни структури бази — лише через **міграції** (історія змін у файлах), а не «руками в кнопках».
- У кожній важливій таблиці є колонка **«філія»**, і правила доступу її враховують.
- Важливі дані **ніколи не видаляємо назавжди** — лише ховаємо + причина при скасуванні.
- База **сама веде журнал змін** (хто / що / коли, було → стало); журнал не редагується.
- **Браузер не пише напряму** у важливі таблиці. (Повторюю, бо це головний урок прототипу.)
- Дати зберігаємо в **UTC**, на екрані показуємо в київському часі.
- На кожну «магію» (автоматичну дію) — **простий тест**, що вона працює.

## 🔌 Кілька програм пишуть в одну картку (AppSheet, MES, 1С)

Картку редагує не лише наш сайт — ще AppSheet (замірники / монтажники), MES (виробництво) і, можливо, 1С. Це нормально, але потребує порядку, інакше програми «б'ються» за ті самі поля. Хороша новина: **правила ми поклали в саму базу, а не в браузер, тому вони діють на всіх, хто пише** — і на наш сайт, і на AppSheet, і на MES.

**Що працює автоматично (бо правила в базі):**
- журнал змін записує будь-яку зміну — хоч від людини, хоч від AppSheet / MES;
- правила доступу (RLS) діють на всіх;
- екрани оновлюються живими (Realtime) на зміну від будь-кого.

**Що треба додати:**

1. **Хто які поля пише («господар» поля).** Найпростіший спосіб уникнути бійки — домовитись, яка програма які поля міняє, і не давати іншим їх чіпати:
   - **MES** → лише статуси / етапи виробництва (ми їх лише читаємо);
   - **AppSheet (замір)** → результати заміру (файли, розміри);
   - **AppSheet (монтаж)** → факт і деталі монтажу;
   - **Google Sheets ("Виробництво", тимчасово)** → статуси виробництва (Pull-only, ми тільки читаємо; ownership belongs to Sheets поки MES не запущений). Push-only: контакти/адреса — ми пушимо туди.
   - **наш сайт** → офісні поля (контакти, адреса, логістика, конструктив) + `external_id` при створенні.
   - **1С** → **немає прямої інтеграції**. `external_id` копіпаститься диспетчером вручну з 1С у форму. API-синхронізація можлива в майбутньому (рік-два, не зараз).

2. **Перевірка правильності статусів — у самій базі (тригер), а не лише в нашій функції.** Щоб навіть AppSheet чи MES не могли поставити картку в неможливий стан, правило «дозволені переходи» ставимо на рівень бази. Тоді воно спрацьовує для **будь-кого**, хто пише — база просто відхиляє недозволену зміну.

3. **Кожній зовнішній програмі — свій окремий обмежений доступ** (свій ключ / користувач бази), а не головний ключ. Тоді правила доступу діють і на неї, а в журналі видно, що змінив саме «MES» чи «AppSheet», а не «хтось».

4. **Зовнішні зміни ідуть через контрольований шлях, а не «в обхід»:**
   - **MES** не пише в нашу базу напряму — він шле повідомлення, а наш «приймальник» (Edge Function) застосовує їх через ту саму перевірку (з номером повідомлення, щоб не задвоїти).
   - **AppSheet / Власний додаток для полів:** також працює суто через наш «приймальник» (API на Edge Functions). Завдяки цьому всі правила і перевірки діють однаково на всіх.

**Чесний нюанс про замок:** замок («Іван редагує») зупиняє лише **інших людей у нашому застосунку**. AppSheet і MES про наш замок не знають. Тому проти зовнішніх програм працює не замок, а **розподіл полів + перевірка версії + живе оновлення**. Приклад: людина редагує картку, а MES тим часом оновив статус виробництва — перевірка версії підкаже людині «дані оновились, онови й повтори», і нічого не загубиться.

## 🔄 Повний шлях замовлення та його петлі

Повний шлях картки тепер описано детально (у ТЗ + `order_stages_and_pause_rules.md`). Нагадування: **весь цей граф — це рядки в таблиці «дозволені переходи»**, тому додається без переписування коду. Але кілька петель потребують **не просто нового статусу, а окремої логіки** — їх виділяю окремо, бо їх легко проґавити.

**Два основні шляхи:**
- **Повний (під ключ):** Створення → Планування заміру → Замір на об'єкті → Конструктив → *(Погодження з клієнтом)* → Виробництво (MES) → Планування монтажу → Монтаж → Закрито.
- **По кресленню (B2B / самовивіз):** Створення → одразу Конструктив (пропуск заміру) → Виробництво → Готово до видачі (пропуск монтажу) → Закрито. *(Пропуск етапів — за типом замовлення.)*

**Петлі й нештатні ситуації (це і є те, що ти просив урахувати):**

1. **Пауза (глобальний рубильник).** Майже на будь-якому етапі до монтажу. Вимагає причину + дату повернення; повертає рівно в той етап, звідки зайшли; таймери заморожуються. *(Вже в плані.)*
2. **Погодження з клієнтом (цикл).** Конструктив → на погодження → якщо правки → назад у Конструктив → знову на погодження… доки не «Затверджено». *Просто кілька переходів у таблиці.*
3. **Хибний виїзд.** Замірник приїхав, а об'єкт не готовий → повертається на Планування заміру (або в Паузу). **Важливо для ЗП:** замірнику все одно нараховується **компенсація за виїзд**, хоча замір не відбувся.
4. **«Проблема» / брак інформації.** Конструктор бачить, що бракує даних → ставить статус «Проблема» → картка блимає в диспетчера, автоматично створюється задача на повторний дзвінок/виїзд. Це **не Пауза** — це активний сигнал «треба втрутитись».
5. **Брак на виробництві.** MES надсилає «проблема / брак» → система блокує планування логістики й підсвічує замовлення керівнику. *(Механізм повідомлень від MES уже в плані.)*
6. **Рекламація / переробка (найскладніша петля — потребує окремої логіки в даних).** Клієнт не прийняв виріб на монтажі → система створює **дочірнє замовлення «Переробка»**, яке:
   - **успадковує креслення** батьківського;
   - отримує **найвищий пріоритет** (Hot);
   - йде **скороченим колом** (Конструктив → Виробництво → Монтаж);
   - а **батьківське замовлення заморожується** — його не можна закрити, поки не завершиться дочірнє.
   Тобто в моделі даних потрібен **зв'язок «батьківське → дочірнє»** між замовленнями (див. Етап 2).
7. **Скасування (із запобіжником).** Скасувати можна лише **до початку виробництва** (поки не ріжуть матеріал), з обов'язковою причиною. Щойно виріб пішов у різку — скасування **блокується машиною станів** і потребує прав **Супер-адміна**. Це конкретне правило закладаємо в перевірку переходів.

> ✅ **Статуси канонізовано за `order_stages_and_pause_rules.md` в Етапі 2.** (Раніше тут було попередження про розбіжність статусів у старих документах — тепер список єдиний і живе в базі).

## 🏗 Етап 1: Фундамент і безпека (найважливіший етап)
*Мета: щоб дані були в безпеці й нічого не губилось. Це база для всього іншого — не поспішати.*

- **Користувач = людина (один список).** Одна таблиця людей, де людина — це і вхід (з роллю), і працівник (з графіком та відділом). *(У прототипі це було двома різними списками — більше так не робимо, інакше зарплату/статистику нема як прив'язати до людини.)*
- **Ролі й доступи (RLS).** Хто що бачить і міняє — правилами в базі, а не в браузері. Нова людина за замовчуванням отримує **мінімальні** права, ніколи не «Адмін».
- **Ієрархія «Регіон → Філія».** Замовлення, люди та склади прив'язані до філій, які входять до регіонів. У доменних таблицях зберігається лише `branch_id` (зв'язок з регіоном через таблицю філій). 
- **Гнучкі права доступу (RLS):** Замість жорсткої прив'язки до ролей (напр. «керівник бачить тільки свій регіон»), доступ до замовлень визначається масивами `allowed_view_regions` та `allowed_action_regions` безпосередньо у профілі працівника. Це дозволяє диспетчеру одного регіону (за дозволом керівника) допомагати в іншому. `SUPER_ADMIN` має значення `NULL` і бачить усе. Також на рівні бази працює жорсткий захист від зміни власних прав.
- **Журнал змін.** Тригери пишуть кожну важливу зміну в окрему таблицю-журнал — хто / що / коли, було → стало, і **джерело** (наш сайт / AppSheet / MES / 1С). Журнал — **лише на читання**, навіть адмін його не редагує. *(Це твій же найперший інстинкт — через тригери — і для Supabase він якраз правильний, бо тригер спрацьовує хоч би хто писав.)*
- **Не видаляємо — ховаємо.** Колонка «приховано»; скасування замовлення **вимагає причину**.
- **Одночасна робота над однією карткою (захист від «затирання»).** Кілька людей часто відкривають те саме замовлення — тому два рівні захисту:
  - *Замок (запобігання):* поки одна людина редагує картку — інші бачать її, але тільки на читання («Іван зараз редагує»). Через 10 хв без дії — автозбереження як чорновик і зняття замка (щоб робота не загубилась).
  - *Перевірка версії (головна гарантія):* у кожної картки є номер версії. При збереженні база перевіряє, чи картку не змінив хтось інший з моменту, як ти її відкрив. Якщо змінив — збереження **відхиляється** з підказкою «хтось уже вніс зміни, онови й повтори». Так нічиї зміни не затираються мовчки — навіть якщо замок протух чи його обійшли.
  - *Живе оновлення (Realtime):* усім, хто тримає картку відкритою, вона оновлюється сама — люди не сидять на застарілих даних.
  - Різні люди, що редагують *різні замовлення* або *різні частини* одного замовлення (адресу vs специфікацію), одне одному не заважають узагалі — бо дані розбиті на окремі таблиці.
  - Зміну статусу база **вишиковує в чергу**: дві одночасні спроби перевести статус не зламають одна одну (спрацює одна, друга побачить уже новий стан).
  - Картку пишуть і **інші програми** (AppSheet, MES) — вони про замок не знають, тому проти них працюють **розподіл полів + перевірка версії** (див. розділ «Кілька програм пишуть в одну картку»).
- **Бекапи.** У Supabase бекапи **вже автоматичні** (на платному тарифі — щоденні). Файли в Storage теж входять у копію. Раз на місяць — **тестове відновлення** (бекап, який не відновлювали — це не бекап).

> ✅ **Контрольна точка (тонкий зріз):** створити 1 замовлення → змінити йому статус через функцію в базі → у журналі з'явився запис → на іншому відкритому екрані дані оновились самі. Якщо це працює — фундамент живий, можна йти далі.

## 📦 Етап 2: Картка замовлення
*Мета: повноцінне замовлення замість прототипних 15 полів.*

- **Розбити на кілька таблиць** (щоб не було 150 колонок в одній): шапка замовлення, контакти, адреса + координати, специфікація (матеріал, площа, вирізи), файли, історія статусів, оплати. Плюс поле **«батьківське замовлення»** — щоб зв'язати рекламацію / переробку з оригіналом (див. петлю «Рекламація»).
- **Правильні типи даних:**
  - внутрішній код UUID + окреме поле `external_id` (Номер з 1С), яке диспетчер копіпастить при створенні. Свій номер не генеруємо — джерело правди для номера це 1С;
  - **площа і гроші — числа, а не текст** (інакше їх не порахуєш для статистики й зарплати);
  - дати — в UTC.
- **Двигун статусів (головне).** Статус міняється **лише через перевірку «дозволених переходів», яка живе в самій базі** (тригер + функція). Тому поставити недозволений статус не може ніхто — ні наш сайт, ні AppSheet, ні MES: база відхилить. Самі переходи — це **дані в таблиці**, тож нові гілки, петлі й цикли (пауза → повернення, погодження → правки → повторне погодження, повторний замір) додаються **без переписування коду**.
  - Функція перевіряє переходи статусів (але перевірка **обов'язкових полів** ВИМКНЕНА для етапу ПРОТОТИПУ, щоб не блокувати тестування флоу).
  - **Запам'ятовує попередній статус** — щоб із «Пауза» повернутись рівно туди, звідки пішли.
  - **Кнопки за статусом:** окрема табличка «що видно / активне на якому статусі». Кнопку, яку не можна натиснути, **ховаємо або робимо сірою** — вона не повинна давати помилку.
  - **Пропуск етапів за типом:** «по кресленню» — пропускає весь замір; «без монтажу» — після готовності одразу «Завершено».
  - `order_stages_and_pause_rules.md` — **головна правда** про статуси. Список статусів у базі звіряємо з ним (щоб не розходились, як було в прототипі).
  - **Повний граф і всі петлі** (пауза, погодження, хибний виїзд, «Проблема», рекламація, запобіжник на скасування) — див. розділ «Повний шлях замовлення та його петлі».
- **Вхід нового замовлення (важлива механіка):**
  - **Перевірка дублів** перед збереженням (нормалізований телефон + ПІБ) — попередити, якщо таке вже є, з опцією «Все одно створити».
  - **Одна картка, без окремого DRAFT-статусу.** Картка створюється одразу в `MEASUREMENT_SCHEDULING` або `ENGINEERING_DESIGN` залежно від типу замовлення. У прототипі обов'язкових полів для переходів немає. Опціональні поля (адреса, специфікація) — можна дозаповнити пізніше.
  - **Файли (PDF/DXF) і парсинг** — відкладено на Етап 5 (там уперше з'являється Storage).
- **Адаптивна картка:** які поля видно — залежить від ролі (керівник бачить усе, оператор — своє). Керується доступами, не «зашито» в код.
- **Зв'язок з 1С:** прямої інтеграції немає. Диспетчер копіпастить номер замовлення з 1С у поле `external_id` при створенні картки. API-синхронізація — можлива опція в майбутньому.
- **Зв'язок з Google Sheets ("Виробництво", тимчасово, до запуску MES):** реалізується як окремий модуль `sheets_sync` через Edge Function. Push-only від нас: контакти, адреса. Pull-only від таблиці: статуси виробництва. Мапінг за іменами колонок, не за індексами. Всі обміни логуються в таблицю `integration_logs`.

## 📖 Етап 2.7: Довідники (Master Data)
*Мета: закласти всі основні довідники системи, які керівник у майбутньому буде наповнювати через UI, а не через розробника.*

**Принцип:** усе, що змінюється в бізнесі («новий матеріал», «нова філія», «нова причина паузи», «нова бригада») — має жити **як рядки в таблицях-довідниках**, а не як хардкод у коді. SQL пишеться один раз (структура таблиці + RLS + RPC для CRUD), далі керівник керує вмістом через UI (Етап 6).

**Що робимо:**

- **Таблиця `materials`** — матеріали виробу (граніт, кварц, кварцит, HPL, акрил, компакт-плита...). Поля: `id`, `name`, `category` (тверді / м'які / плитні — для маршрутизації в потрібний пул конструктора), `is_hidden`, `created_at`.
- **Таблиця `decors`** — декори матеріалу (колір, візерунок). Поля: `id`, `material_id` (зв'язок з матеріалом), `name`, `code_1c` (артикул із 1С), `is_hidden`.
- **Таблиця `pause_reasons`** — довідник причин паузи (замість вільного тексту). Поля: `id`, `name`, `default_days` (стандартна тривалість, наприклад «Чекаємо кухню» = 14 днів), `is_hidden`.
- **Таблиця `brigades`** — бригади монтажників. Поля: `id`, `name`, `branch_id`, `is_hidden`.
- **Таблиця `task_types`** — типи задач у Kanban (Конструктив, Технолог, Розкрій твердих, Розкрій акрилу, Розкрій компакт-плити). Поля: `id`, `name`, `sort_order`, `is_hidden`.
- **Таблиця `cancel_reasons`** — довідник причин скасування замовлення.
- **RLS-політики для довідників:** читати можуть усі залогінені; редагувати — лише `SUPER_ADMIN` (і в майбутньому — керівники своєї філії/регіону, коли керуємо no-code). Захист від видалення системних значень (`is_system = true`).
- **Замість фізичного видалення** — прапорець `is_hidden` (soft-hide), як і в `orders`. Не видаляємо навіть якщо матеріал зняли з виробництва — старі замовлення мають продовжувати бачити свій матеріал.
- **RPC для кожного довідника:** `create_material`, `update_material`, `hide_material` тощо. Через RPC, не прямим INSERT з клієнта (наше залізне правило).

## 📞 Етап 2.8: Комунікація та Активності (Actionable Tasks over Records)
*Мета: відокремити процес комунікації від статусів замовлення, щоб дзвінки і нагадування жили паралельно з виробничим процесом.*

**Принцип:** Замовлення живе своїм життям (FSM - кінцевий автомат), воно рухається по статусах і потрапляє на планування (Ганту). Комунікація — це окрема сутність, яка "прилипає" до замовлення і живе паралельно. Вона **не змінює статусу замовлення**.

- **Сутність "Активність" (Activity):** точкові задачі (дзвінок, SMS, лист, зустріч, внутрішня замітка).
- **Автоматизація:** Замість поля "дата продзвону" в замовленні, система генерує нову Активність типу `CALL` при переходах:
  - Створення нового замовлення (через 4 години).
  - Призначення дати виїзду (за 1 добу до).
  - Постановка на Паузу (за 1 день до планованого виходу з паузи).
- **Робота оператора:** Замовлення та активності виводяться в єдиному списку (впереміш). Диспетчер сортує цей список за **датою найближчої активності**, і опрацьовує їх.
- **Закриття активності:** Вимагає обов'язкового введення **Підсумку (Outcome)** (`ANSWERED`, `NO_ANSWER`, `RESCHEDULED`, тощо) та коментаря. Невиконані активності пропонується перенести.
- **Історія:** Виконані активності назавжди залишаються в Історії Комунікації замовлення, формуючи повний "журнал" спілкування з клієнтом.

**Прив'язка до існуючих таблиць:**
- У `order_specifications` — колонки `material_id`, `decor_id` (FK на довідники, а не текст).
- В історії статусів `PAUSED` — колонка `pause_reason_id` (FK на `pause_reasons`).
- У Kanban-задачах (майбутній Етап 4) — `task_type_id`.

**Seed (початкове наповнення):**
Заллємо базові матеріали, декори, причини паузи — щоб система стартувала не порожньою. Все з прапорцем `is_system = true`, щоб керівник не міг випадково їх видалити (він може лише сховати).

**Verification Plan:**
- Тест: створити матеріал через RPC → з'явився в таблиці → в `audit_logs` є запис.
- Тест: диспетчер намагається створити матеріал → відмова (немає прав).
- Тест: SUPER_ADMIN намагається видалити системну причину паузи → відмова (`is_system = true`).
- Тест: сховати матеріал → в списку матеріалів для нового замовлення його немає → але старе замовлення з цим матеріалом читається без проблем.

**Що НЕ входить у цей етап:**
- UI-екрани керування довідниками (це Етап 6).
- Кастомні поля картки через JSONB (це теж Етап 6).
Поки що керівник керує довідниками через Supabase Studio — це нормально, поки MVP.

## 🧠 Етап 6: No-code керування системою (керівник без розробника)
*Мета: усе, що змінюється в бізнесі (нова філія, новий регіон, нова роль, новий матеріал, новий статус, нове поле картки, зміна прав диспетчера) — керівник робить сам через UI. Без коду, без розробника, без чекання.*

**Принцип:** база готова до цього ще з Етапу 1 і Міграції 8. Усі довідники (Етап 2.7), масиви прав (`allowed_view_regions`, `allowed_action_regions`), таблиці `status_transitions` і `status_required_fields` — це **дані, а не код**. Етап 6 будує над ними охайні екрани керування.

### 6.1 Управління організацією
Керівник додає / редагує / приховує:
- Регіони (Центр, Захід, Польща, ...).
- Філії (кожна прив'язана до регіону).
- Співробітників — заводить нових людей, ставить роль, філію, `allowed_view_regions`, `allowed_action_regions`. Ця частина — критично важлива для сценаріїв типу «завтра відкриваю Варшаву».

**Приклад сценарію відкриття нового регіону (Польща):**
1. Керівник → «Налаштування → Регіони» → «+ Додати регіон» → «Польща» → зберегти.
2. → «Філії» → «+ Додати філію» → «Варшава-Центр», регіон = Польща → зберегти.
3. Новий диспетчер Ivan реєструється в системі (тригер `handle_new_user` створює `profile` з мінімальними правами).
4. Керівник → «Співробітники» → знаходить Ivan → ставить роль `DISPATCHER`, філію `Варшава-Центр`, `allowed_view_regions = [Польща]`, `allowed_action_regions = [Польща]`.
5. Ivan логіниться і бачить **лише польські замовлення**. Українських — жодного. Якщо треба буде помагати Києву — керівник додає `Україна-Центр` у масиви.

**Все це без коду, без міграцій, без розробника.**

### 6.2 Управління довідниками
Керівник керує вмістом таблиць з Етапу 2.7:
- Матеріали (+ категорія: тверді / м'які / плитні → впливає на маршрутизацію в пул конструктора).
- Декори (прив'язані до матеріалу).
- Причини паузи (з дефолтними днями).
- Бригади монтажників.
- Типи задач у Kanban.
- Причини скасування.

Правила: додати може керівник, видалити — не можна (soft-hide), системні значення захищені (`is_system = true`).

### 6.3 Управління машиною станів (для просунутих)
Керівник додає нові статуси або змінює правила переходів:
- Екран «Статуси замовлення» — список усіх статусів, можна додати новий.
- Екран «Дозволені переходи» — таблиця з якого статусу в який, які ролі можуть, які обов'язкові поля.
- Приклад: додати статус «Погодження з архітектором» між `ENGINEERING_DESIGN` і `CLIENT_APPROVAL`.

**Технічно можливо, бо це просто рядки в `status_transitions` і `status_required_fields`.** Але керівник має розуміти, що робить — тому цей екран за замовчуванням прихований і доступний лише `SUPER_ADMIN`.

### 6.4 Кастомні поля картки (JSONB)
Керівник додає **додаткові поля до картки замовлення** без міграції бази:
- Заходить у «Налаштування → Поля картки» → «+ Додати поле».
- Вводить: назва («Колір затирки»), тип (текст / число / вибір зі списку), на якому етапі показувати, обов'язкове чи ні.
- Значення цих полів лежать в `orders.custom_fields` (JSONB) — одна колонка, багато полів.
- Плюс: керівник додає скільки завгодно полів, будь-коли.
- Мінус: за такими полями не можна швидко фільтрувати чи сортувати (для цього треба індекс). Тому:
  - **Основні поля** (за якими шукають, фільтрують, рахують гроші — `external_id`, `phone`, `city`, `area_sqm`, `status`) — це **фізичні колонки** в таблицях. Змінює розробник через міграцію.
  - **Кастомні поля «на подивитись» / «для нагадування»** — JSONB. Змінює керівник.

Якщо кастомне поле стало **дуже важливим** і за ним треба фільтрувати — це сигнал розробнику: «зроби з цього справжню колонку». Стандартна еволюція системи.

### 6.5 Інші розумні штуки (з попереднього плану)
- **AI-помічник:** лише **читає** дані (нічого не змінює!) і бачить тільки те, що дозволено роллю. Ключ — на сервері (в Edge Function), не в браузері.
- **Запис сесій для розбору багів:** з приховуванням особистих даних клієнтів (rrweb).

**Verification Plan:**
- Тест: SUPER_ADMIN створює регіон «Тест» → успіх → в аудиті рядок.
- Тест: диспетчер намагається створити регіон → відмова (немає прав).
- Тест: керівник дає новому користувачу доступ на регіон → користувач бачить замовлення того регіону.
- Тест: керівник додає кастомне поле → воно з'являється в картці замовлення на потрібному етапі.
- Тест: керівник додає новий статус у машину станів → перехід через `change_order_status` з цим статусом працює.

- **Само-лікування:** Система спершу сама повторює завислі повідомлення й знімає мертві замки, і лише якщо не вдалось — пише тобі. Менше нічних побудок через дрібниці.
- **Сторож сторожів (Ловимо тишу):** Кожна задача (напр. бекап) звітує «я відпрацювала». Якщо вона мовчить — це алерт. Плюс один зовнішній пінг (через GitHub Actions): якщо впаде сам Supabase і внутрішній сторож замовкне, зовнішній пінг обов'язково заб'є тривогу.
- **Робот-зловмисник:** За розкладом бот сам пробує зламати доступ (підвищити роль, зайти в чужу філію, перестрибнути статус). Якщо щось вийшло — червоний алерт. Це постійна перевірка рівно тієї діри, що вбила прототип.
- **Авто-перевірка бекапу:** Робот сам розгортає копію й звіряє дані, замість того щоб ти робив restore-drill руками.
- **Сторож витрат:** Ловить, коли щось «роздулось» (велика кількість запитів, переповнення Storage), до того як прилетить великий рахунок від Supabase.
- **Розумні алерти та Ранкова зводка:** Сповіщення мають рівні 🔴/🟠/🟢 + зранку ти отримуєш одне повідомлення-зводку. Це рятує від утоплення в 500 алертах і дозволяє за 10 секунд зрозуміти, що система жива.
- **Синтетичні тести ("Шпигуни") та Логування шлюзів:** Робот імітує користувача для перевірки процесів, а всі запити від MES/AppSheet/1С осідають в таблиці інтеграцій. Жоден байт не проходить непоміченим.

## ✅ Як перевіряємо (просто)

- **Після Етапу 0:** Supabase локально стартує, фронт підключається.
- **Після Етапу 1 — головні перевірки безпеки** (це там, де горів прототип):
  - звичайний користувач **не може** зробити себе адміном;
  - **не бачить** чужу філію;
  - **не може** перестрибнути статус в обхід правил;
  - **не може** видалити дані «назавжди» (тільки ховання);
  - журнал змін заповнюється і не редагується.
- На **кожну автоматичну дію** (нагадування про паузу, сповіщення, авто-маршрут у розкрій) — простий тест, що вона спрацьовує, ще до додавання в «бойову» гілку.
- Раз на місяць — тестове відновлення з бекапу.
