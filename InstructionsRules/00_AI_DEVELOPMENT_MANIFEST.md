# SlabCut Planner: Маніфест Розробки (AI Development Guidelines)

Цей файл є обов'язковим для прочитання будь-яким ШІ-асистентом (Antigravity, Claude Opus/Sonnet, ChatGPT), який підключається до розробки проєкту **SlabCut Planner**.

## 1. Зафіксований Стек Технологій (STRICT LOCK)
Будь-які пропозиції змінити цей стек відхиляються автоматично.
- **База Даних / Бекенд:** Supabase (PostgreSQL).
- **Бізнес-логіка бази:** SQL (PL/pgSQL), Triggers, RLS (Row Level Security), `pg_cron`, `pgmq`. Жодних зовнішніх серверів черг (Redis, BullMQ, RabbitMQ).
- **Серверна логіка (API шлюзи):** Supabase Edge Functions (Deno / TypeScript).
- **Фронтенд:** React + Vite + TypeScript.
- **Стилізація (CSS):** Vanilla CSS / CSS Modules. 
- **UI Компоненти:** Для інтерактивних елементів з нетривіальною доступністю (випадайки, діалоги, комбобокси) — **Radix UI**; для календаря — **FullCalendar**; для канбану — **@dnd-kit/core**.
- **Заборонено:** Tailwind CSS, Bootstrap, NestJS, Express.js.

## 2. Архітектурне правило: "Товста база, дурний клієнт"
- **Браузер ніколи не довірений.** Фронтенд React є просто відображенням.
- Всі складні перевірки статусів, прав доступу, захист від колізій пишуться виключно на рівні PostgreSQL (через функції RPC, тригери та політики RLS). 
- Навіть якщо хакер (або інша система, наприклад AppSheet) спробує змінити статус напряму, база повинна відбити цей запит.

## 3. Зовнішні інтеграції (AppSheet, MES, 1C)
- Зовнішні системи ніколи не ходять у таблиці напряму.
- Вони відправляють стандартизований JSON на нашу Edge Function ("приймальник"). 
- Edge Function перевіряє payload і викликає безпечну RPC-функцію в базі.
- Всі зміни обов'язково пишуться в таблицю `audit_log` (Журнал змін) із зазначенням `source` (UI, AppSheet, MES, System).

## 4. Дизайн та Ергономіка
- **WOW-дизайн** (glassmorphism, мікро-анімації, яскраві градієнти) використовується ТІЛЬКИ на екранах, де мало даних і людина проводить мало часу (логін, презентаційні дашборди керівника).
- **Робочі зони (Таблиці, Канбан, Розклад):** Там, де диспетчер працює по 8 годин, дизайн має бути максимально щільним, чистим і висококонтрастним (ергономіка > естетики). Скло і анімації тут ЗАБОРОНЕНІ, щоб не заважати читанню даних.

## 5. Взаємодія AI (Колаборація декількох ШІ)
- **Користувач (Domain Expert)** формулює бізнес-болі та архітектуру бази.
- **Інші AI (напр. Claude, ChatGPT)** можуть виступати як Senior Architect — рев'ювити ідеї, шукати логічні діри, давати поради по оптимізації.
- **ШІ-Асистент / Gemini (ви)** виступаєте як Lead Developer — імплементуєте поради у код, створюєте файли, виконуєте міграції, але **ігноруєте поради, якщо вони суперечать пункту 1 (Tech Stack)**.

## 6. Обов'язкова Фіксація (Documentation & Changelog)
- Після кожного завершеного кроку розробки, зміни архітектури або виправлення багу, ШІ-агент **ЗОБОВ'ЯЗАНИЙ** зафіксувати це в документації.
- Усі нові сутності, прийняті рішення та змінені зв'язки повинні негайно оновлюватись у відповідних документах архітектурного плану (у теці `C:\hhgh\PLM module\InstructionsRules`).
- **Завжди звіряйтеся з файлом `CURRENT_STATE.md`**, щоб розуміти, на якому етапі знаходиться проєкт, перш ніж щось міняти.
- Жодна зміна логіки не повинна залишатись лише "в коді". Код і архітектурні плани мають бути завжди синхронізовані на 100%.
