### 9. Статуси, Підстатуси та Логіка Паузи
*Реалізовано на основі нових вимог щодо візуальної ідентифікації та обробки пауз.*
- **Вихід з паузи (Зміна статусу):** При зміні статусу з "На паузі" на будь-який інший (через кнопку "Play"), логіка тепер викликає `resume_order`, що автоматично повертає замовлення у його `previous_status`, а не просто ставить статус `UNPAUSED`.
- **Підстатуси "Планування заміру":** Для етапу `MEASUREMENT_SCHEDULING` розроблено систему підстатусів (відображаються як бейджі справа вгорі на картці):
  - **"Нове"**: Замовлення без дати (не перетягнуте на календар). Має світло-синій бейдж.
  - **"Попередньо заплановано"**: Замовлення, яке перетягнуто на календар, але не закріплене за замірником. Має помаранчевий (янтарний) бейдж та відображає під собою планову дату.
  - **"Пауза замір"**: Замовлення, що потрапило на паузу з етапу планування. Має червоний бейдж, під яким виводиться дата виходу з паузи (`resume_date`) та час 10:00.
- **Дизайн карток (OrdersList):**
  - "Корішок" (ліва вертикальна смужка статусу) для всіх замовлень на етапі `MEASUREMENT_SCHEDULING` (вкл. "Нове" і "Попередньо заплановано") завжди залишається синім `var(--accent-color)`, щоб зберігати приналежність до етапу.
  - Сама картка отримує жовтуватий фон (`#fefce8`) тільки у випадку, якщо вона "Попередньо запланована" (isDraft).
- **Сортування:** Додано сортування "За датою планування (від найближчих)" (`schedule_date`), яке сортує замовлення по їх `scheduled_date` (від ближчих до дальших), а ті, що без дати - залишає в кінці.
- **Логіка паузи в календарі:** При постановці на паузу, замовлення автоматично "падає" в календар на `resume_date` на 10:00 ранку без вказаного замірника (реалізовано через `fakePausedTasks` у `CalendarPanel`). Це дозволяє візуально контролювати паузи без фізичного створення `measurement_tasks`. **УВАГА: Це тимчасовий MVP-хак, який підлягає видаленню після впровадження повноцінних Активностей (order_activities) в Етапі 2.8.**

#### 11.2 Взаємодія з базою даних (Supabase)
Всі компоненти налаштувань використовують підхід прямої взаємодії з БД через `supabase-js`:
1. **Читання (Select):** При монтуванні компонента (`useEffect`), викликається `supabase.from('table_name').select('*')`. Наприклад, `GlobalRegionsSettings.tsx` витягує дані з таблиць `regions` та `branches`. Для відображення зв'язків (скільки філій у регіоні) використовуються JOIN-запити або локальне фільтрування масивів.
2. **Запис (Insert/Update):** При створенні нового регіону чи філії викликається `supabase.from('regions').insert([{ name }])`.
3. **Видалення (Delete):** Використовується `supabase.from('branches').delete().eq('id', id)`. (Примітка: для критичних сутностей, як замовлення, ми використовуємо `is_hidden = true`, але для простих довідників типу філій на даному етапі може застосовуватись фізичне видалення, якщо немає зв'язаних даних).
4. **Обробка завантаження:** Кожен компонент має локальний стейт `loading` (boolean), щоб показувати спінер або текст "Завантаження..." доки Supabase поверне дані. Помилки перехоплюються через `catch` і виводяться користувачу через `alert()`.
